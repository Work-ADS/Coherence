## Why this exists

In the Overview, **Liquidez** and **Objetivo de legado** are shown as plain numbers because there is no progress/meter primitive. They are value-vs-target quantities — the natural piece is a horizontal meter (filled track against a rail) that reads "how far toward the goal" at a glance.

## What this session produces

1. **`afi-meter-v2`** in `libs/ui/src/meter-v2/` — 3-file convention + `.variants.ts` + `index.ts`, exported from `@coherence/ui`. `foundations-modern` tokens only; `[data-foundation="modern"]` scope. Value-vs-target progress with a tone.
2. **A workbench section** in `apps/site/src/app/pages/demos/foundations-modern-workbench/` — every tone × a spread of fill percentages (0 / partial / at-target / over-target), on the `data-foundation="modern"` root.

## Proposed API — lock first thing

```
label     : string            // "Liquidez"
value     : number            // current value (raw, for the aria + ratio)
max       : number            // target / 100% point
valueText : string            // optional pre-formatted display ("45.000 € / 60.000 €"); if omitted, no text row
tone      : 'default' | 'success' | 'warning' | 'critical'  // fill color; OPEN: manual tone vs. auto-derived from value/max thresholds
```
Decisions to lock (one at a time): (a) is tone **manual** (consumer passes it) or **threshold-derived** (e.g. <50% warning)? Recommend manual — keeps the primitive dumb, thresholds are a product concern. (b) Does over-target (value > max) clamp the fill at 100% or show overflow styling? (c) Is the numeric readout inside the primitive or projected? Recommend a simple `valueText` input, formatting done by the caller (consistent with stat-tile-v2 and card-v2).

## Tokens — token-guardian gate REQUIRED

This primitive introduces the DS's first progress track. Expect to add component tokens at the correct layer (semantic → component), e.g. `--meter-track-height`, `--meter-track-radius`, `--meter-rail-background`, `--meter-fill-{default,success,warning,critical}`. Bind fills to existing semantic/data-viz roles (`--success-*`, `--warning-*`, `--critical-*` / data-viz) rather than inventing raw colors. **Every new token and every new `var(--…)` in `libs/ui/**` must go through `ds-token-guardian` before commit** — this is the highest-token-risk of the three primitives. No raw hex/px (pre-commit hook blocks it).

## a11y

Use a real progress semantic: `role="progressbar"` (or a native element) with `aria-valuenow`/`aria-valuemin`/`aria-valuemax` and an accessible name from `label`. Fill must not be the only signal — the `valueText` carries the numbers. Check fill-vs-rail contrast for each tone.

## Constraints

Motion: if the fill animates on mount, use `--motion-*` tokens (`prefers-reduced-motion` respected). RAE copy for demo labels. Pre-flight before handoff; tester verifies.

## Out of scope

Circular/radial gauge (donut is its own brief), segmented/stepped meters, threshold auto-tone (unless locked in), the Overview recompose, doc page, dark-mode values.
